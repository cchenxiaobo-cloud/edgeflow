## 1. 系统概述与设计目标

### 1.1 这是什么（一句话）

EdgeFlow 是一个**云边两级架构**的边缘计算平台：云端（CloudCore）负责统一管理，边缘（EdgeCore）负责就近处理，即使**断网也能继续干活**。

通俗类比：云端像"总部"，边缘节点像"分公司"。总部下发任务、收集汇报；分公司平时与总部通信，但**断网时分公司也能自己运转**，网络恢复后再向总部补报。

### 1.2 与 KubeEdge 的关系

EdgeFlow 借鉴 KubeEdge 的整体架构（CloudHub/EdgeHub 云边通信、Edged 边缘运行时、DeviceTwin 设备影子、MetaManager 本地存储等概念，参考 <https://kubeedge.io/docs/architecture/>），但**以本项目自身设计为准**，差异点：

| 维度 | KubeEdge | EdgeFlow（本项目） |
|------|----------|-------------------|
| 边缘消息总线 | MQTT Broker（mosquitto） | **NATS**（Leaf Node 模式，MQTT 兼容层，⚠️ 待 POC 验证，WBS 3.6） |
| 消息序列化 | Protobuf | **M1 先 JSON，规模化后升级 Protobuf**（WBS 4.1/4.4） |
| 云端元数据 | apiserver + etcd | 同样以 Kubernetes apiserver（etcd）为唯一事实源 |
| 开发阶段安全 | 默认 mTLS | **M1 用 Token 过渡，M4 才上 mTLS**（WBS 7.1/7.4） |

### 1.3 三大设计目标

| 目标 | 含义 | 对应模块（WBS） | 验收锚点（ROADMAP §5） |
|------|------|----------------|------------------------|
| **云边协同** | 云端统一管控：节点注册、应用下发、状态收集 | 2.3/2.4/2.1/3.1 | 节点注册后 `kubectl get nodes` Ready；心跳 ≤30s |
| **边缘自治** | 断网期间边缘继续运行，恢复后自动同步 | 3.4、3.3 | 断网 30min 容器持续运行；恢复 120s 内同步 |
| **设备管理** | 设备接入、数字孪生（设备影子）、远程控制 | 5.x、2.2、3.5、3.6 | 端到端设备状态上报延迟 ≤5s |

### 1.4 总体设计原则

1. **云边同源**：云侧完全基于 Kubernetes 生态（CRD/apiserver），不另造一套 API；边缘是"轻量 K8s 运行时"而非独立平台。
2. **消息总线解耦**：组件之间不直接互相调用，通过消息总线（NATS）通信，保证模块可独立开发、替换（WBS 4.3）。
3. **零依赖起步**：当前 Go 1.26.2 纯标准库；第三方依赖（NATS、SQLite 驱动）按需引入并先做 POC（WBS 3.6 前置 POC）。
4. **协议先行**：云边通信协议（WBS 4.1）是关键路径第一步，先定义后实现（ROADMAP §2.1 关键路径）。

**读图要点（新手向）**：

- **云侧两大部分**：`Kubernetes 控制面`（apiserver/etcd，K8s 自带）+ `CloudCore`（本项目自己的云端程序）。CloudCore 不直接读写 etcd，只通过 apiserver 的标准 API 工作——这是"云边同源"原则的体现。
- **边侧一个进程**：EdgeCore 是一个二进制、内部多个模块（对应 KubeEdge 的 EdgeCore 多模块设计）。所有模块的"对外通信"都经过 EdgeHub 这一个出口，便于统一做重连、加密。
- **云边之间的唯一通道**：EdgeHub ↔ CloudHub 的 WebSocket 连接（端口 10000）。NATS、SQLite 都是**各自一侧内部**的设施，不跨云边。

## 3. 关键数据流

### 3.1 下行：云 → 边（应用/配置下发，M1/M2）

```
用户 kubectl apply（Deployment/ConfigMap/Secret）
   │
   ▼
apiserver ──watch──► EdgeController（WBS 2.3）──► 生成 PodSync/ConfigSync 消息
                                                     │
                                                     ▼
                                               CloudHub（WBS 2.1）
                                                     │  WebSocket 通道（:10000）
                                                     ▼
                                               EdgeHub（WBS 3.1）
                                                     │
                                                     ▼
                                              MetaManager（WBS 3.3）──► 写入 SQLite（本地持久化）
                                                     │
                                                     ▼
                                                Edged（WBS 3.2）──► 容器运行时：创建/更新/删除容器
```

要点：
- **MetaManager 先落盘再执行**：即使 Edged 还没就绪，数据也不会丢；重启后从 SQLite 恢复。
- **只下发增量**：MetaManager 与云端比对资源版本号（resourceVersion），只同步变更部分（WBS 4.4 增量同步）。

### 3.2 上行：边 → 云（状态/设备数据上报，M1/M3）

```
边缘设备 ──MQTT──► EventBus（WBS 3.6）
                    │
                    ▼
              DeviceTwin（WBS 3.5）──► 更新设备影子（reported 状态）
                    │
                    ▼
              MetaManager（WBS 3.3）──► 暂存 + 去重
                    │
                    ▼
              EdgeHub（WBS 3.1）──► DeviceReport 消息
                    │  WebSocket 通道
                    ▼
              CloudHub（WBS 2.1）──► NATS 消息总线
                    │
                    ▼
        DeviceController（WBS 2.2）──► 更新 Device CRD 状态
                    │
                    ▼
              apiserver（kubectl get device 可见最新状态）
```

Pod 状态上报（PodStatus）走同一条链路，终点是 Node/Pod 状态。

### 3.3 自治模式：断网期间（M2，WBS 3.4）

```
  断网事件
     │
     ▼
EdgeHub 检测连接断开（心跳超时）
     │
     ├─► 自治引擎接管：标记"离线模式"
     │       │
     │       ├─► Edged 继续按 SQLite 中的元数据维持容器运行（不重启、不漂移）
     │       ├─► 设备数据照常采集 → DeviceTwin/EventBus 写入本地（暂存，带时间戳）
     │       └─► 状态变更记录到本地"待同步队列"（带递增序号）
     │
  网络恢复
     │
     ▼
EdgeHub 重连成功（60s 内，指数退避）──► 重新 Register + 全量版本比对
     │
     ▼
自治引擎按"待同步队列"增量补报（PodStatus/DeviceReport），
云端按消息 id 去重（幂等），冲突按策略解决（⚠️ 策略待定：默认"云端期望为准 + 本地补报"）
```

验收锚点（ROADMAP §5 WBS 3.4）：断网 30min 容器持续运行；恢复后 120s 内完成同步。

## 4. 云边通信协议设计（草案，WBS 4.1）

> 本节是 **WBS 4.1（消息协议设计）的输入草案**：消息格式、类型枚举、路由主题、可靠性语义。**以本文档为准先评审，评审通过后进入代码实现**。当前 M0 无云边通信。

### 4.1 传输通道

- 传输层：WebSocket，端口 **10000**（云边唯一通道；与 healthz 管理端口 8080 分离）。
- 方向：边缘主动发起连接（EdgeHub 客户端 → CloudHub 服务端），云端不反向拨号——边缘常处于 NAT 之后，只能主动出网（与 KubeEdge 一致）。
- 连接管理（WBS 4.2）：心跳间隔 ≤30s；断线后指数退避重连（1s/2s/4s/…上限 60s）；同一节点同一时刻只允许一个活跃连接（旧的踢掉，防双连接脑裂）。

### 4.2 消息信封格式（JSON，v1）

所有消息统一外层信封，业务数据放 `payload`：

```json
{
  "id": "9f8c1e2a-...",        // 消息唯一 ID（UUID），ACK 关联 + 幂等去重键
  "type": "Heartbeat",         // 消息类型（见 §4.3 枚举）
  "version": "v1",             // 协议版本，用于平滑升级（JSON → Protobuf 时靠它兼容）
  "source": "node-edge-001",   // 来源标识：cloud 或节点 ID
  "target": "cloud",           // 目标：cloud / 节点 ID / 广播组
  "timestamp": 1755168000000,  // 毫秒时间戳
  "correlationId": "",         // 关联 ID：请求-响应配对（如 Register ↔ RegisterAck）
  "payload": { }               // 类型相关负载（见下表示例）
}
```

**为什么先 JSON**：零依赖、可读、新手友好、调试成本低；**为什么能升级 Protobuf**：信封带 `version` 字段，序列化层（WBS 4.4）做成可替换实现，协议语义不变，只换编码。

### 4.3 消息类型枚举（草案）

| type | 方向 | 用途 | 关键 payload 字段（草案） | 里程碑 |
|------|------|------|--------------------------|--------|
| `Register` | 边→云 | 节点注册（连接建立后第一条） | nodeID、arch、os、edgecoreVersion、资源量 | M1 |
| `RegisterAck` | 云→边 | 注册结果 | accepted、nodeName（云端分配的 K8s 节点名）、token 校验结果 | M1 |
| `Heartbeat` | 边→云 | 心跳保活 | 时间戳、负载摘要（可捎带状态） | M1 |
| `HeartbeatAck` | 云→边 | 心跳应答（含云端侧节点状态） | nodeStatus（Ready/Unknown） | M1 |
| `PodSync` | 云→边 | Pod 配置下发（创建/更新/删除） | pod 清单、operation（add/update/delete）、resourceVersion | M1/M2 |
| `ConfigSync` | 云→边 | ConfigMap/Secret 下发 | 名称、命名空间、数据（Secret 加密/引用传递） | M2 |
| `PodStatus` | 边→云 | Pod 状态上报 | podUID、phase、容器状态、重启次数 | M1/M2 |
| `DeviceReport` | 边→云 | 设备数据/状态上报 | deviceName、twin 状态、采集数据 | M3 |
| `DeviceCommand` | 云→边 | 设备操作指令（Twin desired 变更） | deviceName、属性、期望值 | M3 |
| `NodeJob` / `NodeJobResult` | 云→边 / 边→云 | 任务分发与结果回收（⚠️ WBS 2.8 归属待确认） | jobID、命令/脚本、超时 | 待定 |
| `Ack` | 双向 | 通用确认（配合 §4.5 可靠投递） | ackID（=被确认消息的 id）、code、error | M1 |

> 枚举是**开放集合**：`type` 字段按字符串匹配，新增类型不改信封结构、不破坏旧版本（协议兼容性，WBS 10.3 API 兼容矩阵的通信侧对应物）。

### 4.4 路由主题草案（WBS 4.3 消息路由引擎）

协议层用 `type` 路由；消息进入各侧 NATS 后按主题（topic）路由。主题草案：

```
edgeflow.cloud.edge.{nodeID}.register     # 注册（边→云）
edgeflow.cloud.edge.{nodeID}.heartbeat    # 心跳
edgeflow.edge.{nodeID}.pod.sync           # Pod 下发（云→边）
edgeflow.edge.{nodeID}.config.sync        # 配置下发
edgeflow.edge.{nodeID}.device.{deviceName}.report    # 设备上报
edgeflow.edge.{nodeID}.device.{deviceName}.command   # 设备指令
edgeflow.cloud.broadcast.{group}          # 云端广播（如全量升级指令）
```

主题与 type 的关系：**type 决定"这条消息是什么"（语义），topic 决定"谁该收到"（路由）**。实现时先按 type 分发，topic 由 NATS 侧细化（WBS 4.3 评审确认）。

### 4.5 可靠投递（WBS 4.6）

- 语义：**QoS 1（至少一次）+ 幂等去重**（与 ROADMAP 完成标准"QoS 1 消息不丢失（ACK/重试生效）"一致）。设备指令类关键消息（DeviceCommand）可升级 QoS 2（恰好一次，M3 评审）。
- 机制：
  1. 发送方为每条消息生成 `id`（UUID），入本地"待确认队列"；
  2. 接收方处理后回 `Ack`（携带 ackID）；超时（默认 5s）未收 → 指数退避重试（上限 3 次，⚠️ 参数待定）；
  3. 接收方按 `id` 去重：重复消息直接回 Ack 不重复执行（幂等）。
- 离线缓冲：边侧待确认队列持久化到 SQLite（配合自治引擎 §3.3），断网期间的消息不丢，恢复后补发。

### 4.6 序列化演进路径

```
M1: JSON（信封 + payload 全 JSON）   ← 开发调试期，零依赖
M2+: 按需对 payload 做 gzip/snappy 压缩（WBS 4.4，先做压缩后做编码替换）
M4/规模化: Protobuf 编码（信封保留 version 字段，同一通道渐进升级，WBS 4.4）
```

## 5. 配置管理策略

### 5.1 现状（M0 已实现，pkg/config）

优先级模型（**命令行 > 环境变量 > 配置文件 > 默认值**），cloudcore 端口示例：

| 优先级 | 来源 | 示例 | 说明 |
|--------|------|------|------|
| 1 | 命令行 | `./bin/cloudcore --port 9090` | 显式指定后不再看其他来源 |
| 2 | 环境变量 | `EDGEFLOW_CLOUDCORE_PORT=9090` | 命名约定：`EDGEFLOW_{组件}_{键}` |
| 3 | 配置文件 | `config/cloudcore.json`（`{"port": 9090}`） | 文件不存在静默回落；存在但解析失败**报错退出**（防止用户配错还不知情） |
| 4 | 内置默认值 | `8080` | 端口范围 1-65535 校验 |

### 5.2 扩展规划（各组件 + 热重载）

1. **每个组件一份配置**：`config/cloudcore.json`、`config/edgecore.json`（M1 新增），结构按组件定义（如 edgecore 需要 `cloudhub.url`、`nodeID`），加载逻辑统一复用 pkg/config 的优先级模型（WBS 1.5 共享库扩展）。
2. **敏感配置不入文件**：证书路径、节点 Token 等通过环境变量 / K8s Secret 注入（M4，配合 §6），配置文件只放非敏感项。
3. **动态配置与热重载**（WBS 2.7，M4）：云端配置支持 `SIGHUP` 热重载；下发到边缘的配置走 ConfigSync 消息（§4.3），不走文件。

## 6. 安全设计（现状与规划）

> 安全是 M4 里程碑交付（WBS 7.1-7.5、4.5），但**从 M1 第一行通信代码起就要预留安全位**（消息信封的 source 字段、Token 校验点）。

### 6.1 现状（M0）

- 无任何认证：`/healthz` 仅健康检查，默认绑定 `:8080`（开发期可接受，**禁止生产暴露**）。
- 云边通道尚未存在（M1 才建）。

### 6.2 M1 过渡方案（开发期，弱认证）

- 边缘节点 `keadm join` 时向云端申请一次性 **Token**（keadm 与云端 API 交互，WBS 8.6）；
- EdgeHub 连接 CloudHub 时携带 Token，CloudHub 校验通过才接受注册（对应 WBS 4.5 基础版 + 7.4 的节点验证雏形）；
- 传输层开发期用明文 WebSocket（仅限内网/本地开发拓扑，见 docs/DEV-ENV.md）；**明确标注：未认证节点连接必须被拒绝**（ROADMAP §5 WBS 7 完成标准的开发期预演）。

### 6.3 M4 完整方案（生产化）

| 安全项 | 方案 | WBS |
|--------|------|-----|
| CA 与证书生命周期 | 自建 CA（keadm 初始化）；为每个节点签发证书，有效期 90 天、提前 30 天自动轮换（⚠️ 周期参数待定） | 7.1 |
| 云边认证 | **mTLS 双向认证**：CloudHub 验证 edgecore 证书、edgecore 验证 CloudHub 证书；证书轮换不中断连接 | 7.4、4.5 |
| 权限控制 | RBAC：按角色限制云边消息类型与 CRD 操作（如只读节点只能上报不能下发） | 7.2 |
| 设备认证 | 设备注册 Token + 设备证书（Mapper 接入时校验） | 7.3 |
| 审计日志 | 关键操作（注册、登出、指令下发、证书签发）记录审计日志，可查询 | 7.5 |
| 传输加密 | 生产环境 WebSocket 走 TLS（wss://） | 4.5 |

## 7. 可扩展性设计

### 7.1 模块边界原则

1. **每个组件一个独立包**：`cmd/` 下是进程入口，业务实现放独立包（当前已实践：healthz 在 pkg/httpx 而非 main.go，见 docs/CODE-REVIEW.md 的评审结论）；组件之间**不直接跨进程调用**，只通过消息总线（云侧 NATS / 边侧 NATS Leaf Node）通信。
2. **协议向后兼容**：新增消息类型 = 加一个枚举值 + 一个处理函数，不破坏旧版本（§4.3）。
3. **接口先行**：跨模块边界（如 MetaManager 的存储、EventBus 的消息源）先定义 interface，再实现具体后端——这是 NATS/SQLite 可替换的前提。

### 7.2 NATS 接入点（⚠️ POC 验证后确认，WBS 3.6 前置）

| 接入点 | 位置 | 用途 |
|--------|------|------|
| 云端消息总线（hub） | 云 | CloudHub 收到的消息投递到 NATS，各控制器（EdgeController/DeviceController）订阅消费；反向亦然 |
| 边缘 Leaf Node | 边 | EdgeCore 各模块（Edged/DeviceTwin/自治引擎）之间的本地消息路由 |
| **MQTT 兼容层** | 边 | NATS 原生支持 MQTT 协议接入：设备/Mapper 直接以 MQTT 连 EventBus，无需额外 Broker。**兼容性需 POC**：设备用 MQTT 3.1.1 发布/订阅，验证 QoS、保留消息、遗嘱消息行为 |

若 POC 不通过，回落方案：边缘独立部署 MQTT Broker（mosquitto）+ 桥接 NATS（⚠️ 备选，WBS 3.6 评审决定）。

### 7.3 SQLite 接入点

- 唯一使用方：**MetaManager（WBS 3.3）**。存储层定义为 interface（`Store`：Get/List/Watch/Update 元数据 + 待同步队列）。
- 默认实现 SQLite（本地文件，如 `/var/lib/edgeflow/edgecore.db`）；因接口隔离，未来可换 bbolt/Badger 等嵌入式存储（纯 Go 驱动优先，避免 CGO 阻碍交叉编译）。
- SQLite 数据范围（M1 起）：节点信息、下发的 Pod/ConfigMap/Secret 缓存、设备影子、待同步队列。**不含**容器运行数据（由运行时自己管）。

### 7.4 CRD 与 Mapper 扩展

- CRD 族（WBS 1.4 定义，apis/ 目录）：`Node`（边缘节点）、`DeviceModel`（设备型号/协议描述）、`Device`（设备实例 + 孪生状态）、`NodeJob`（任务，⚠️ 归属待确认）。新增能力 = 新增 CRD + 对应控制器，不侵入现有模块。
- Mapper 框架（WBS 5.1）：设备接入以 Mapper 插件形式实现（SDK 提供注册/注销、数据上报、指令接收接口），Modbus/OPC-UA/MQTT 各是独立 Mapper，互不影响。
