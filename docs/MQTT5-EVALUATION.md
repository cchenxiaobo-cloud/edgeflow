# EdgeFlow MQTT 5.0 特性评估

- 文档版本：对应 EdgeFlow v0.27.0（QoS2 持久化版本线）
- 文档性质：**评估文档（仅评估，不实现）**
- 撰写日期：2026-09-01
- 结论速览：**v0.27.0 范围裁定为「不实现 MQTT 5.0」**，本文件记录评估依据，供后续版本决策参考。

---

## 1. 背景与本评估的定位

### 1.1 EdgeFlow 当前 MQTT 能力全貌（截至 v0.27.0）

EdgeFlow 的 MQTT 栈为**自研零第三方依赖实现**，经 v0.24.0 → v0.27.0 四个版本逐步演进：

| 能力 | 状态 | 说明 |
| --- | --- | --- |
| MQTT 3.1.1 协议 | 已具备 | CONNECT / SUBSCRIBE / PUBLISH / PINGREQ 等全套报文编解码（`pkg/mqtt`） |
| QoS 0 / 1 / 2 | 已具备 | QoS2 为 opt-in 的 EXACTLY ONCE 四次握手（PUBREC / PUBREL / PUBCOMP） |
| TLS / mTLS | 已具备 | v0.25.0 引入 TLS，v0.26.0 补齐客户端证书双向认证 |
| QoS2 持久化 | 已具备（本轮） | v0.27.0 将 QoS2 暂存状态落盘，跨重启可恢复 |
| 进程内 sim broker | 已具备 | `pkg/mqttsim`，支持 QoS0/1/2、TLS、按连接隔离的 QoS2 暂存 |
| 订阅型 mapper | 已具备 | `mappers/mqtt`，`EDGEFLOW_MQTT_*` 环境变量 + `EDGEFLOW_MQTT_CONFIG` 配置文件驱动 |
| 协议版本 | **仅 3.1.1** | 尚无 MQTT 5.0 支持 |

### 1.2 本评估的定位

- 本文件**只做评估与推演，不包含任何实现**。v0.27.0 的版本范围裁定结论为：本轮不引入 MQTT 5.0，保持 3.1.1 能力线与既有冻结测试不变。
- 文中所有「改造点」「风险」均基于 EdgeFlow 现有代码结构与 MQTT 5.0 OASIS 官方规范公开内容推演，不涉及任何第三方评测数字。
- 任何分期建议均为**草案**，不构成版本承诺。

## 2. MQTT 5.0 相对 3.1.1 的核心新特性清单

以下七项特性逐条给出对 EdgeFlow 的价值判断（或不适用的理由）。

### 2.1 属性系统（Properties / User Properties / Content Type）

- 5.0 在多种报文中引入属性区，支持 User Properties（自定义键值对）、Content Type、Payload Format Indicator、响应主题等。
- **对 EdgeFlow 的价值**：中等偏高。User Properties 可用于边缘侧打标（设备 ID、站点、采样时间戳等），与 mapper 的数据富化场景契合；Content Type 有助于 payload 语义自描述（如 `application/json`）。
- **成本提示**：属性区是变长编码，现有编解码器需新增「属性解析/序列化」通用层，是编解码面最大的增量之一。

### 2.2 原因码（Reason Code）

- 5.0 在 CONNACK / SUBACK / PUBACK / DISCONNECT 等报文中携带细粒度原因码（如 0x87 未授权、0x8A 主题名无效）。
- **对 EdgeFlow 的价值**：高。边缘部署排障（鉴权失败、ACL 拒绝、QoS 不支持）目前只能靠连接断开与日志推断，原因码可显著提升可观测性；实现成本相对可控，适合作为 5.0 化的第一批落地项。

### 2.3 会话与过期（Session Expiry Interval / Clean Start）

- 5.0 将「会话」与「连接」解耦：Clean Start 控制是否复用既有会话，Session Expiry Interval 控制断连后会话存续时长（3.1.1 中仅有 cleanSession 布尔量，断连即二选一）。
- **对 EdgeFlow 的价值**：高。边缘网络不稳定场景下，QoS1/2 离线消息依赖会话存续；可配置的会话过期直接对应「断网重连后补发」这一典型边缘需求。
- **成本提示**：这是**语义级改造**，会话状态机需与连接生命周期分离，涉及 client 与 sim broker 双侧（详见第 3 章）。

### 2.4 共享订阅（Shared Subscriptions）

- 5.0 支持 `$share/{ShareName}/{Filter}` 订阅形式，多条订阅者负载分摊消费同一主题流。
- **对 EdgeFlow 的价值**：中等。多实例 EdgeFlow 节点分摊上游数据流（如多个网关共同消费同一下行指令流）时有用；单节点场景收益有限。
- **适用性备注**：EdgeFlow 自研 sim broker 侧需实现共享订阅的路由语义（轮询/粘性等分发策略），client 侧成本较低。

### 2.5 主题别名（Topic Alias）

- 5.0 允许以短整型别名替代重复的长主题名，降低报文开销。
- **对 EdgeFlow 的价值**：中低。边缘带宽受限且高频发布场景有价值，但 EdgeFlow 典型主题长度有限，收益与实现复杂度（别名表管理、0 别名无效语义、broker 侧别名上限协商）不成正比。可列为低优先级。

### 2.6 流控（Receive Maximum / Flow Control）

- 5.0 通过 Receive Maximum 限制未确认 PUBLISH 的在途数量（QoS1/2），实现双向流控。
- **对 EdgeFlow 的价值**：高。边缘设备内存受限，在途未确认报文无上限时存在内存膨胀风险；Receive Maximum 与既有 QoS2 opt-in 状态机天然契合，是「资源保护型」特性，建议纳入优先实现集合。

### 2.7 增强认证（Enhanced Authentication, AUTH 报文）

- 5.0 引入 AUTH 报文与认证方法/数据属性，支持 SASL 风格的多轮质询-响应认证（如 SCRAM）。
- **对 EdgeFlow 的价值**：中低（当前阶段）。EdgeFlow 已具备 TLS/mTLS，传输层身份已可闭环；增强认证的收益在于应用层凭证不落明文、信道绑定等，可待有明确客户需求后再评估。
- **成本提示**：AUTH 引入「连接中认证」状态机，改动面覆盖 client 与 broker 双侧，且零依赖实现需自带具体认证方法（如 SCRAM），工程量不小。

## 3. 与 EdgeFlow 架构的适配点分析

### 3.1 `pkg/mqtt` 报文编解码层（packet 层）

- 3.1.1 报文头中固定头与可变头边界清晰；5.0 的 Property Length 为变长整数（Variable Byte Integer），需在可变头之后、载荷之前插入统一的属性编解码段。
- 扩展点评估：现有编解码函数按报文类型组织，建议新增**独立的属性编解码单元**（读取属性 ID → 分发到具体属性解析），避免在每种报文的解码函数中散落 if-else。
- 原因码字段仅存在于部分报文且为可选出现，解码器需兼容「3.1.1 报文无原因码 / 5.0 报文有原因码」两种形态——这直接引出第 4 章的版本协商问题。

### 3.2 `pkg/mqtt` 客户端配置（client Options 扩展点）

- 现有 Options（broker 地址、TLS/mTLS、QoS、cleanSession、QoS2 opt-in 开关等）需扩展为可承载 5.0 语义：协议版本选择、Session Expiry Interval、Receive Maximum、User Properties 注入点等。
- 关键原则（延续 EdgeFlow 硬约束传统）：**新增字段默认值必须等价于当前 3.1.1 行为**，即默认协议版本仍为 3.1.1，5.0 字段在 3.1.1 模式下不生效且不编入报文。

### 3.3 `pkg/mqttsim` sim broker 会话语义改造点

- 当前 sim broker 的会话语义是「**会话即连接**」：连接建立即创建会话，断开即随连接清理（QoS2 暂存亦按连接隔离）。
- MQTT 5.0 要求会话与连接解耦：同一会话可跨越多次连接，Session Expiry Interval 决定断连后会话存活期；QoS1/2 的待确认与排队消息附着于**会话**而非连接。
- **最大改造面判定**：「QoS2 暂存由按连接隔离改为会话级隔离」是与 5.0 会话语义对齐的**最大单点改造**——v0.27.0 刚完成的 QoS2 持久化数据结构需要重新划定归属键（连接标识 → 会话标识），并增加会话过期回收逻辑。此项改造同时影响持久化文件格式与既有的按连接测试断言。

### 3.4 `mappers/mqtt` mapper 配置新增项

- 若引入 5.0，`EDGEFLOW_MQTT_*` 环境变量族与 `EDGEFLOW_MQTT_CONFIG` 配置文件需新增（草案，仅列举）：`EDGEFLOW_MQTT_PROTOCOL_VERSION`、`EDGEFLOW_MQTT_SESSION_EXPIRY`、`EDGEFLOW_MQTT_RECEIVE_MAXIMUM`、User Properties 键值对配置段。
- 配置兼容性要求：未配置上述新项时，行为必须与 v0.27.0 **逐字兼容**（默认协议版本 3.1.1、无会话过期、无流控限制）。

## 4. 互通与迁移风险

### 4.1 5.0 broker ↔ 3.1.1 client 互通性

- 方向一（现状即成立）：EdgeFlow 3.1.1 client 连接支持多版本的 5.0 broker（如主流开源 broker）。broker 依据 CONNECT 报文中的协议版本字段识别 3.1.1 客户端并**向下兼容**，此为 MQTT 5.0 规范定义的协议版本协商行为，互通风险低。
- 方向二（升级后断裂）：EdgeFlow client 升级为 5.0 后，将**无法连接旧版 sim broker**（`pkg/mqttsim` 仅实现 3.1.1 报文形态，无法解析 5.0 的属性区/原因码）。即 client 侧 5.0 化与 sim broker 侧 5.0 化必须**同版本成对交付**，否则冻结测试与本地验证链路断裂。

### 4.2 冻结测试的兼容策略

- v0.24.0 / v0.25.0 / v0.26.0 全套冻结测试对报文编解码与连接行为有逐字节级断言，5.0 化不得触碰其断言。
- 建议策略（草案）：
  1. **协议版本参数化**：协议版本作为编解码器与 Options 的显式参数，默认值恒为 3.1.1；
  2. 冻结测试路径上所有报文构造/解析函数在默认参数下产出与历史版本**逐字一致**的字节序列；
  3. 5.0 行为以新增测试集覆盖，与冻结测试集物理隔离。

### 4.3 其他迁移风险

- 持久化格式风险：会话级隔离改造将改变 QoS2 暂存的归属键，v0.27.0 持久化文件的升级读取策略需在实现期单独裁定。
- 文档与运维风险：`EDGEFLOW_MQTT_*` 新增环境变量会扩大配置面，需同步更新 mapper 使用文档与示例。

## 6. 结论与分期建议

### 6.1 范围裁定结论

- **v0.27.0 不实现 MQTT 5.0。** 理由：本轮核心交付为 QoS2 持久化，5.0 引入的会话解耦将与其数据结构归属键直接冲突，强行同轮叠加将同时扩大两处的验证面并危及冻结测试零改动约束。

### 6.2 分期草案（非承诺）

以下仅为建议草案，是否立项、版本号与时点均以后续版本规划为准：

- **第一阶段（暂记 v0.29.0，草案）**：协议版本参数化 + 原因码 + Receive Maximum。
  - 依据：三者共享「默认 3.1.1 不变、增量可选」的演进路径，风险最低；原因码与流控对边缘可观测性与资源保护收益即时可见。
- **第二阶段（暂记 v0.30.0，草案）**：会话与连接解耦（Session Expiry Interval / Clean Start）+ sim broker 会话级隔离 + 共享订阅。
  - 依据：这是语义级大改，需独立一轮完成 client 与 sim broker 成对改造，并重整 QoS2 持久化归属键。
- **暂缓项**：主题别名、增强认证（AUTH）——收益与当前边缘场景匹配度较低，待明确需求再评估。

### 6.3 一句话结论

EdgeFlow 的 3.1.1 能力线（QoS0/1/2、TLS/mTLS、sim broker、mapper 配置、QoS2 持久化）已相对完整；MQTT 5.0 的核心增量价值集中在**原因码、流控与会话解耦**三点，其中「会话级 QoS2 隔离」是最大改造面，建议按上述草案分两期推进，**本轮（v0.27.0）不做**。
